## 2. What `.gitignore` protects against, and why each group matters

| Group | Patterns | Why it matters *here* |
|---|---|---|
| Build output | `target/`, `*.war`, `*.class` | `bloodbank.war` is 56 MB; committing it would make the repository unusable and would defeat the point of a reproducible build |
| **Database files** | `*.mv.db`, `*.trace.db`, `data/` | The H2 file is created the first time the application runs locally. Committing it would version-control patient and donor data and would cause a merge conflict on every run |
| Secrets | `*.pem`, `*.jks`, `.env`, `ansible/vault_pass*` | Registry credentials come from Jenkins credential bindings, never from a file in the repository |
| Test output | `surefire-reports/`, `failsafe-reports/`, `screenshots/` | Regenerated by every build; only the curated copies under `evidence/` are committed, because those are the submission's proof |
| IDE / OS | `.idea/`, `.vscode/`, `.DS_Store` | Machine-specific noise; `.DS_Store` in particular appears in every macOS directory |
| Local overrides | `application-local.yml`, `scripts/local-*.sh` | Lets a developer override configuration without ever risking a commit of it |

`.gitattributes` normalises line endings to LF for all text files and marks binaries, so the same
repository builds identically on macOS, a Linux CI agent and Windows. `.editorconfig` fixes
indentation per file type.

## 4. Issue templates

| Template | Purpose | Notable field |
|---|---|---|
| `task.md` | One of the 15 subject tasks | Copies the task sheet's *Deliverable* line verbatim, plus an "evidence to capture" list, so nothing in the wording is missed |
| `feature_request.md` | A user story from the backlog | Acceptance criteria must be written Given/When/Then and tagged `[U]` / `[S]` / `[A]` for the kind of test that will prove each one |
| `bug_report.md` | A defect | Requires naming the **requirement being violated** (e.g. FR-08) and will not accept a fix without a test that would have caught it |
| `config.yml` | Disables blank issues and links to the docs and the Definition of Done | Forces every issue through a template |

The pull-request template requires a table mapping each acceptance criterion to the test that
proves it, and ends with the `--no-ff` merge command, so the merge style cannot drift.

## 6. The application skeleton, and why it is deliberately this small

The skeleton contains **no domain logic at all**. Its only job is to prove, before any feature
work begins, that the artefact builds and serves traffic in all three run modes. Debugging a build
problem and a business-logic problem at the same time is what makes the later tasks slow.

What it establishes:

| Element | Established now because |
|---|---|
| `packaging = war` with `finalName = bloodbank` | The Jenkins job, the `Dockerfile` and the Ansible playbook all refer to `target/bloodbank.war`; fixing the name now means no later task has to change |
| `SpringBootServletInitializer` | Makes the WAR runnable three ways with no profile switching (NFR-10) |
| `application.yml` with environment-variable overrides | Satisfies the parameterised-environment requirement of Task 8 structurally, instead of adding a build profile later |
| `/actuator/health` unauthenticated | The container `HEALTHCHECK`, the Ansible `uri` check and the Jenkins post-deploy check all need it without credentials (FR-26) |
| `context-path: /` | Deployed as `ROOT.war`, so every URL is identical in every environment and the Selenium journeys need no rewriting |
| Smoke test | Three assertions: the context loads, the landing page identifies the project, and health reports `UP`. If this test fails, nothing downstream is worth debugging |
| `src/it/java` present but empty | The Selenium source root exists from the start, so Task 9 adds tests rather than restructuring the build |
